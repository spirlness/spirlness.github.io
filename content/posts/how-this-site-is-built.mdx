## Why Static

This site is a single question answered over and over: what is the simplest thing that can serve an academic homepage reliably? The answer settled on a fully static build — [Next.js](https://nextjs.org) 16 in `output: "export"` mode, deployed to GitHub Pages via Actions. There is no server, no runtime database, no CMS. Every page you can reach was rendered at build time and uploaded as an `index.html`.

The constraint sounds limiting, and in exchange it buys three things: the site cannot go down in any interesting way, every page is fast by construction, and the entire deploy is reproducible from a clean checkout with `npm ci && npm run build`.

## Content as Files

Nothing lives in a CMS. Every piece of content is a plain file in the repository, read from disk at build time:

| Source | Route |
|---|---|
| `content/posts/*.mdx` | `/blog/<slug>/` |
| `content/projects/*.json` + optional `.mdx` | `/projects/<id>/` |
| `content/updates/*.json` | the homepage timeline |
| `content/references.bib` | `/publications` and in-post citations |

The filenames *are* the URLs, which means the URL space is validated before anything ships: slugs must match `^[A-Za-z0-9-]+$`, project ids must equal their filenames, and a dead internal link fails the build rather than silently 40ing.

<SideNote>
The homepage timeline is intentionally separate from blog posts — publishing a post does not automatically announce it. Add an entry under `content/updates/` if it deserves a spot there.
</SideNote>

## The MDX Pipeline

Posts are MDX compiled through `next-mdx-remote`: remark-math and rehype-katex render `$...$` and display equations, rehype-pretty-code highlights fenced code blocks with Shiki, and a small custom plugin rewrites `[@bibtexKey]` citations into numbered markers linked to a references section at the end of the post.

```text
Consider a system governed by [@zhang2023efficient] ...
                    |
                    v
Consider a system governed by [2] ...
```

The citation keys resolve against a real `references.bib` parsed at build time, so the reference list on `/publications` and the citations inside posts come from the same source. An unknown key is a build error, not a rendered placeholder — dead citations cannot reach production.

Interactive components — orbit controls, simulations — are wired into the MDX component map and lazily loaded client-side, keeping the three.js payload out of pages that never ask for it.

## The Layout

The typography follows the Distill journal pattern: a centre column capped at 800px, headings in a display face, section rules on `h2`, and margin notes in the gutter on wide viewports. The gutter layout is plain CSS grid — `1fr min(800px, 100%) 1fr` — with the margin notes positioned absolutely against the centre column. Below 1400px viewport width the gutter is too narrow for notes and a table of contents, so they collapse into inline and hidden forms respectively rather than overflowing.

## Verification

The deploy pipeline runs the full gate on every push to `master`: lint, unit tests over the content layer, the production build, then a verification pass over the exported artifact — every required page, every per-post and per-project `index.html`, the sitemap, `robots.txt`, the RSS feed, and the Open Graph card. If any of it is missing, the deploy stops before GitHub Pages ever sees it.

## Publishing a Post

The whole authoring loop is now two commands:

```bash
npm run new-post -- my-post-slug --title "My Post"
npm run lint && npm test && npm run build   # the CI gates, locally
```

The first scaffolds a validated MDX file in `content/posts/`; the second reproduces exactly what CI will run. Push to `master` and the site deploys itself.
