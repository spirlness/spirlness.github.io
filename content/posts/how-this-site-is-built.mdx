## 为什么选择静态

本站在反复回答同一个问题:**什么是最简单、又能稳定支撑一个学术主页的方案?** 最终答案是全静态构建——运行于 `output: "export"` 模式的 [Next.js](https://nextjs.org) 16,通过 GitHub Actions 部署到 GitHub Pages。没有服务器,没有运行时数据库,没有 CMS。你能访问到的每一个页面,都是在构建时渲染完成、以 `index.html` 形式上传的。

这个约束听起来限制重重,但换来三样东西:站点不存在"宕机"这种故障模式;每个页面天然就是快的;整个部署可以从干净检出用 `npm ci && npm run build` 完整复现。

## 内容即文件

没有任何内容存放在 CMS 里。每一篇内容都是仓库中的纯文本文件,在构建时从磁盘读入:

| 内容来源 | 对应路由 |
|---|---|
| `content/posts/*.mdx` | `/blog/<slug>/` |
| `content/projects/*.json` + 可选同名 `.mdx` | `/projects/<id>/` |
| `content/updates/*.json` | 首页时间线 |
| `content/references.bib` | `/publications` 与文内引用 |

文件名*就是* URL,这意味着 URL 空间在上架前就完成了校验:slug 必须匹配 `^[A-Za-z0-9-]+$`,项目 id 必须与文件名一致,失效的站内链接直接构建失败,而不是静默变成 404。

<SideNote>
首页时间线与博客文章刻意分离——发布一篇文章并不会自动上首页公告。若值得在首页出现,需在 `content/updates/` 下另行添加条目。
</SideNote>

## MDX 管线

文章是 MDX,经 `next-mdx-remote` 编译:remark-math 与 rehype-katex 渲染 `$...$` 行内及独立公式,rehype-pretty-code 用 Shiki 为代码块着色,还有一个自定义插件将 `[@bibtexKey]` 引用改写为带编号的上标标记,链向文末的参考文献列表。

```text
考虑一个由 [@zhang2023efficient] 刻画的系统……
                    |
                    v
考虑一个由 [2] 刻画的系统……
```

引用键在构建时对真实的 `references.bib` 解析,因此 `/publications` 的文献列表与文内引用同出一源。未知的键会触发构建错误,而非渲染出一个占位符——死引用到不了生产环境。

交互组件(轨道控制、仿真演示)注册在 MDX 组件映射里,按需在客户端懒加载,three.js 的体积不会进入从未用到它的页面。

## 版式设计

排版沿用 Distill 期刊的范式:中栏上限 800px,标题用展示字体,`h2` 带章节分隔线,宽视口下栏外空白处放旁注。栏外布局是纯 CSS Grid——`1fr min(800px, 100%) 1fr`——旁注相对中栏绝对定位。视口宽度低于 1400px 时栏外空间放不下旁注和目录,二者分别折叠为行内形式与直接隐藏,而不是任其溢出。

## 验证

每次向 `master` 推送,部署流水线都会跑完整的关卡:lint、内容层单元测试、生产构建,再对导出产物做一轮核查——所有必需页面、每篇文章和每个项目的 `index.html`、sitemap、`robots.txt`、RSS 订阅、Open Graph 分享卡。任何一项缺失,部署都会在 GitHub Pages 收到任何东西之前中止。

## 发布一篇文章

整个写作-发布闭环如今只剩两条命令:

```bash
npm run new-post -- my-post-slug --title "我的文章"
npm run lint && npm test && npm run build   # 在本地预演 CI 关卡
```

前者在 `content/posts/` 下生成一份通过校验的 MDX 骨架;后者与 CI 执行的完全一致。推送到 `master`,站点便会自行完成部署。
